# Архитектура ML-сервиса


## 1. Выбранный архитектурный подход

Для данного проекта выбран монолитный подход.

Это значит, что API, загрузка модели и получение предсказаний находятся в одном приложении. 
Такой вариант подходит потому, что сервис небольшой и решает одну основную задачу: предсказание дефолта клиента.

Преимущества монолитного подхода для этого проекта:

- простая структура проекта
- легко запускать локально
- удобно упаковывать в Docker-контейнер
- проще тестировать
- не требуется настраивать несколько отдельных сервисов

Микросервисная архитектура для текущего проекта была бы избыточной. 
Она больше подходит для крупных систем, где разные части приложения развиваются отдельно.

Все основные функции объединены в одном Flask-сервисе.


## 2. Возможное использование RabbitMQ

В production-среде RabbitMQ можно было бы использовать для асинхронной обработки задач.

Например:
Пользователь - Flask API - RabbitMQ queue - ML worker - Сохранение результата

Такой подход был бы полезен, если:

- нужно обрабатывать много запросов
- предсказание занимает много времени
- нужно масштабировать обработку задач.

Пример сценария:

1. Пользователь отправляет данные клиентов
2. Flask API не выполняет предсказание сразу, а кладёт задачу в очередь RabbitMQ
3. Отдельный worker забирает задачу из очереди.
4. Worker загружает модель и выполняет предсказание
5. Результат сохраняется в базу данных или отправляется обратно пользователю.

RabbitMQ также можно использовать для передачи событий, логов и задач на переобучение модели.

## 3. Логирование

Основная информация о работе сервиса выводится в консоль. При запуске через Docker эти логи можно смотреть через команду:

docker logs <container_id>

В production-версии проекта логирование можно расширить.

Можно логировать:

- время запроса
- endpoint
- статус ответа
- входные данные без персональных данных клиента
- результат предсказания
- вероятность дефолта
- ошибки приложения
- время обработки запроса.

Логи можно хранить в структурированном JSON-формате. Такой формат удобен для поиска, фильтрации и анализа.

## 4. Мониторинг

Для production-среды можно использовать систему мониторинга и сбора логов.

Один из вариантов это ELK-стек:

- Elasticsearch - хранение логов
- Logstash - сбор и обработка логов

С помощью мониторинга можно отслеживать:

- количество запросов к API
- количество ошибок
- среднее время ответа
- долю предсказаний класса 0 и класса 1
- изменение распределения входных признаков

## 4. DVC

DVC - это инструмент для контроля версий данных и моделей.

В обычном Git удобно хранить код, но большие датасеты и модели хранить сложнее. DVC помогает отслеживать версии таких файлов отдельно.

В данном проекте DVC можно было бы использовать для версионирования:

- исходного датасета
- обработанных данных
- сохранённой модели

## 5. MLflow

MLflow - это инструмент для отслеживания экспериментов машинного обучения.

С его помощью можно сохранять:

- название модели
- параметры модели
- метрики качества
- версию датасета
- сохранённые артефаты модели
- дату и время запуска эксперимента.

В данном проекте MLflow можно было бы использовать для сравнения нескольких моделей

## 6. Бизнес-метрики

Кроме технических метрик модели, важно учитывать бизнес-метрики.

- Снижение ожидаемых финансовых потерь

Одна из основных бизнес-метрик - снижение ожидаемых финансовых потерь.

Если модель заранее определяет клиента с высоким риском дефолта, банк может:

- отказать в выдаче кредита
- уменьшить кредитный лимит
- запросить дополнительные проверки
- предложить другой продукт с меньшим риском.

Метрику можно оценивать как разницу между ожидаемыми потерями без модели и ожидаемыми потерями после внедрения модели.


- Доля одобренных заявок при допустимом уровне риска

Если модель хорошо отличает надёжных клиентов от рискованных, банк может:

- сохранить приемлемый уровень риска
- не снижать слишком сильно количество одобренных заявок
- увеличить качество кредитного портфеля.
